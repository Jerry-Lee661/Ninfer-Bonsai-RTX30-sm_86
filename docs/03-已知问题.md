# 已知问题与规避

## 1. DFlash2 在 serve 路径的每轮开销异常（未解决）

现象：命令行界面（ninfer.exe）跑 DFlash2 5 drafts 在英文负载约 233 t/s；同一份工件放进
ninfer-serve 只有 65.8 t/s，而其验收率仍为 71%（每轮 4.85 token）。

定位：投机本身在 serve 里是工作的（请求日志有 `mixed speculation accepted`，`/stats` 的
`decode_rounds` 与 `committed_decode_tokens` 比值是 4.85），问题在每轮耗时：serve 的投机轮约
73.7 ms，而命令行约 18 到 20 ms。MTP 投机在 serve 里没有这个问题（MTP 2 drafts 就是
103.8 t/s）。

规避：部署用 MTP（`--spec mtp --draft-tokens 2` 到 5），它已经覆盖契约线；需要 DFlash2 的
长文场景可以先用命令行验证收益。

## 2. 中文负载投机收益小

DFlash2 与 MTP 的投机对英文和代码更有效。中文负载实测验收率 20% 到 38%，英文 58% 到 73%。
中文场景建议 `--draft-tokens 2`，把轮开销压到最低。

## 3. KV 量化与状态精度组合未重测

早期实验里 `--kv-dtype rk4v4` 与 `--gdn-state-fp16` 的组合读数（低于默认约 15%）是在解析器
缺陷存在时取得的，只对"第一个旗标生效"的旧二进制有意义。修复后这两种设置需要重新测量。
长上下文（超过约 8K）仍然需要 rk4v4 之类的 KV 量化来控制显存。

## 4. 显存与上下文

12 GB 卡上：权重 7.99 GiB（含投机头），默认 KV 池 8K token 时运行占用约 1 GiB。开
`--max-context 32768` 之前先确认可用显存，或用 KV 量化。

## 5. 已知的上游差异

- 上游 README 的 Highlights 表口径是"单请求 greedy，除非该行另有说明"；引用数字时注意
  8 并发那几行是聚合吞吐。
- ninfer-all 与本仓使用的工件是 PQ2/t2 谱系；Prism 的 PTQ1_0 工件是另一档打包，两者权重值
  相同（我们做过逐元素验证），但 PPL 与内核路径不同，数字不要混用。

## 6. 为什么预编译包比别的 ninfer 发行版大（812 MB 对约 545 MB）

与 Don-Chad/ninfer-3090 的 v0.6.1-rtx3090 Windows 包（545 MB）对比过构成，差异全部来自功能面：

| 项 | 本包（ninfer-all 合并线 + 三元移植） | Don-Chad v0.6.1-rtx3090 |
|---|---|---|
| 主程序 | ninfer-serve.exe 1228 MB | ninfer-serve.exe 184 MB |
| 嵌入 GPU 代码 | **276 个 cubin，14165 个内核**，约 1.2 GB SASS（`__nv_fatbin` 节） | .nv_fatbin 63 MB + `__nv_relfatbin` 114 MB（重定位设备码残留） |
| 三元（t2）内核 | 有（`t2_small_t` / `t2_rowsplit` / `t2_g128_fp16`） | **完全没有**（跑不了 Bonsai 三元工件） |
| DFlash2 / ngram / disk-KV | 有 | 无 |
| ffmpeg 运行库 | 自编 63 系全编解码器，141 MB | 精简 62 系，19 MB |

也就是说：本包必须携带**整个三元内核家族**（外加合并线的媒体/视觉、MoE、各量化族路线、DFlash2 等），
而 v0.6.1 是面向 Qwen3.8 的 W8/INT8/nvfp4 精简线，两者用途不同。

包内确实没有可压缩的"水分"：无调试符号表、无多余架构（只有 sm_86）、PTX 占比极小
（抽取 SASS 合计 1231 MB，与 `.nv_fatbin` 1195 MB 基本相等）。

若只做纯文本推理、不需要视觉/视频，可以自行用 `-DNINFER_DISABLE_MEDIA=ON` 重编，
省掉约 141 MB 的 ffmpeg/curl 运行库。
